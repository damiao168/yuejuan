# 动态风控与验证器管理：证据、交互和上线门槛

核对日期：2026-09-14。本文对应当前工作树的账号安全切片，不表示已部署。研究服务于中国教师的学校公共电脑、个人手机和高频阅卷工作流；所引海外服务研究不是本项目的效果证明，也不是国内合规结论。

## 本轮决策

管理端已补齐可选 TOTP 注册、一次性恢复码保存、关闭与重新生成的操作挑战。继续保持 `EDUGRADE_MFA_ENABLED=false`，风险处置仍为 `off/shadow`。验证器管理与“所有登录受到 MFA 保护”必须明确区分，不能通过 UI 勾选或风险分数宣布达到某认证等级。

| 不确定问题 | 一手证据与局限 | 项目采用的决策 |
| --- | --- | --- |
| 设置验证器是否容易？ | [Reese 等，SOUPS 2019](https://www.usenix.org/conference/soups2019/presentation/reese)：72 人两周模拟银行登录，另有 30 人实验室设置研究。总体评价较好，但场景与人口样本不代表中国教师。[论文结论](https://www.usenix.org/system/files/soups2019-reese.pdf)还记录了 TOTP 输入超时问题。 | 使用简明中文、二维码与手动密钥并列、单个 6 位输入框保留前导零。说明动态码将刷新、成功码不能复用和手机时间核对；不因 UI 超时问题扩大后端验证窗口。 |
| 教师怎样保存恢复码？ | [Höltervennhoff 等，USENIX Security 2024](https://www.usenix.org/conference/usenixsecurity24/presentation/h%C3%B6ltervennhoff)：281 名端到端加密邮箱用户问卷与 197 条支持请求分析，发现多种保存策略，以及丢失、取用困难和安全误解。邮箱用户具有自选择偏差，不能把其偏好直接当作教师偏好。 | 提供主动复制、明文下载与手动离线保存选择，不默认打印或自动下载。明确保存位置需要独立可访问；复制／下载不等于安全保存。离开前本地确认保存，或明确放弃；勾选不作为“安全证明”。 |
| 如何说明手机丢失？ | [Gerlitz 等，SOUPS 2023](https://www.usenix.org/conference/soups2023/presentation/gerlitz-adventures)：设置并检查 78 个服务的恢复交互，发现不少服务在设置时不说明第二因素丢失，也缺少可见入口。专家检查不是教师用户实验。 | “关闭验证器／手机丢失”始终可见，允许当前密码加未使用恢复码验证关闭。说明该码验证成功即消耗，即使取消后续操作也不能复用；手机和所有码都丢失时，没有已交付的人工重绑工具，不制造管理员可以自动解决的承诺。 |
| 应直接照搬其他产品的流程吗？ | [Lyastani 等，NDSS 2023](https://www.ndss-symposium.org/?p=13181)：常见网站在第二因素设置和使用旅程上存在混合、不一致的模式。通用惯例不必然代表优质体验。 | 统一使用“身份验证器”“动态码”“恢复码”，保持明确操作名称与步骤。设置、保存、验证、执行分别呈现，成功提示说明究竟完成哪一步。 |
| 验证码还是自动链接跳转？ | [Wiefling 等，IFIP SEC 2020](https://arxiv.org/abs/2008.07795)：592 人研究比较基于邮箱的再认证方式，初次接触 magic link 时焦虑高于代码方式。不能据此证明 TOTP 优于所有链接、短信或 Passkey。 | 本项目已有 TOTP 接口，采用显式输入与操作说明，不增加缺少供应商和账号绑定基础的邮件链接流程。验证只产生指定操作的短期授权，随后必须再次点击确认，不自动重放业务命令。此分步执行是项目安全设计推论，不是该论文直接结论。 |
| 是否每次阅卷都需要二次认证？ | [Wiefling 等，ACSAC 2020](https://arxiv.org/abs/2010.00339)：65 人实验室研究中，所研究 RBA 变体的可用性评价优于所研究 2FA，安全感也有提升；安全感不等于攻击防护效果。 | 仍以少打断教学工作为目标，未来按高风险登录和高影响操作引入挑战，不在每次保存分数时加验证。当前不启用任何业务 MFA 策略。 |
| 能直接使用论文阈值或准确率吗？ | [Wiefling 等，ACM TOPS](https://arxiv.org/abs/2206.15139)：超过一年、330 万用户和 3130 万次登录，研究配置优化与隐私特征。大规模单服务数据不代表学校 NAT、批量开考、浏览器升级和冷启动账号。 | 现有分数仅为可解释规则，不是已校准的盗号概率；保留影子模式。上线前按学校、会话类型、账号历史量分层评估挑战率、误伤率、成功率和恢复工单，不直接移植其阈值，也不把合成攻击结果当作真实精确率。 |
| 少量黑盒测试能证明线上 RBA 吗？ | [Makowski、Pöhn，2023](https://arxiv.org/abs/2308.15156)：重测三家服务发现账号创建差异及许多难以触发的案例，说明黑盒观察有复杂条件与覆盖限制。 | 测试“换 IP 没有弹框”不能单独证明实现安全或不安全。验证策略版本、特征来源、历史不足、处置建议和实际执行链路；影子阶段记录建议但不改变授权。 |

## 标准参考，不作合规背书

[NIST SP 800-63B-4 的认证器生命周期要求](https://pages.nist.gov/800-63-4/sp800-63b/events/)覆盖绑定、恢复、撤销及独立通知，并要求保存型恢复码随机生成、摘要保存、限速和使用后失效。本项目已有高熵一次性码与数据库原子消费，但只有账号页审计活动，没有经验证的独立通知地址／可靠通知渠道；当前单验证器与仅用于关闭的恢复路径也不是完整 NIST 恢复体系。不能宣称符合 AAL2、NIST 或已通过国内合规审查。

[OWASP MFA 指南](https://cheatsheetseries.owasp.org/cheatsheets/Multifactor_Authentication_Cheat_Sheet.html)强调因素更换必须验证既有因素，不能只信任已登录会话，并应通过独立渠道通知。项目据此保留当前密码加现有因素的管理边界、禁止直接覆盖已启用凭据。恢复码仅用于受限关闭，不授权重新生成、全局认证提升或其他业务；普通密码恢复也不清除已启用因素。

[RFC 6238](https://www.rfc-editor.org/rfc/rfc6238)规定成功验证后不能再次接受相同 OTP。前端提示等待新码，但真正的防重放仍由数据库最后消费步长、挑战状态和事务检查保障，不能靠按钮禁用或浏览器时钟保证。

TOTP 并不抗实时钓鱼，也不能防止已被控制的浏览器读取注册密钥。保持后续高权限账户 Passkey／企业 IdP 路线，注册二维码不能上传第三方服务。本文只根据上述证据作有限推论，没有用论文认知评分推导实测攻击成功率。

## 前端秘密生命周期与失败恢复

- 七个 MFA 请求使用固定认证接口、Cookie、CSRF、自带 `AbortSignal` 和 `cache: no-store`，等待上限为 30 秒；没有 React Query 缓存、Web Storage、秘密 URL 或通用幂等键。后端仍是唯一授权边界。
- 流程控制器仅驻留组件内存，密码和用户输入的 OTP 不进入流程快照。注册确认成功后删除注册密钥视图，替换为仅本次响应提供的恢复码；关闭、组件卸载、切换账户、注册／挑战到期或 `pagehide` 清除当前流程，忽略晚到响应。恢复码展示额外最多 10 分钟，隐藏不等于作废服务器上的码。
- `AbortController` 不能回滚已发出的服务端请求。网络断开、未知 5xx 或响应不符合约定时，丢弃授权并刷新状态，不自动重试。启用／重新生成结果丢失时，只能核对是否启用，再使用验证器发起新的重新生成操作，不能取回同一次秘密响应。
- 明确的验证拒绝可在同一挑战内重试，仍受服务端次数和聚合限速约束。验证成功与最终执行分开；执行失败后不继续保留该授权用于自动重放。
- 复制与下载只有用户点击时发生；明文文件需由用户移至安全位置并清理下载目录。页面无法保证剪贴板历史、扩展、操作系统或截图中的副本消失，也不自动覆盖用户剪贴板。切换去保存恢复码的个人密码管理器不强制清空当前展示，以免反而导致恢复码不可保存。
- 关闭验证器成功后，前端调用既有登出处理，清理会话、查询缓存和阅卷草稿后备数据；后端原子撤销全部会话／设备及因素关联。公共电脑／服务会话禁用管理入口，接口仍独立拒绝。

## 下一阶段启用门槛

1. 完成学校真实用户的小规模测试，覆盖不同年龄／技术熟悉度、手机不可用、共享电脑、验证码即将刷新、恢复码无法取用和响应丢失。观察任务成功率与恢复耗时，不把本轮模拟浏览器验收视作教师可用性验证。
2. 落实独立安全通知、联系人验证和可追踪失败投递；绑定、恢复码替换／使用、因素撤销等事件在账号被接管后仍有机会被本人发现。现有安全活动页不是独立通知。
3. 设计并演练丢失全部因素的人工核验、审批、延迟、通知、因素重绑和全会话撤销，限定管理员权限及审计；不能只加一个“管理员重置 MFA”按钮。
4. 完成密钥与数据库联合恢复、受控重加密／密钥版本管理以及回滚演练。保持未配置时失败关闭，不借用模型凭据主密钥。
5. 从影子数据生成经分层校准的阈值与误伤预算，先审查个别高影响操作，再灰度策略。后续业务挑战的灰度回滚不能放宽仍启用的验证器管理、一次性消费、CSRF 或会话撤销控制。

## 补充调研：独立通知、账号补救与可信边界

### 为什么安全活动页不能替代通知

[Bhattacharya 等，USENIX Security 2026](https://www.usenix.org/conference/usenixsecurity26/presentation/bhattacharya)检查 100 个热门服务的账号安全界面：29 个没有可区分账号访问的界面；在提供设备或位置描述的 61 个服务中，41 个可被伪造信息混淆。样本以热门通用服务为主，不代表本项目或中国学校，但能否定“浏览器名称／IP 位置就是可靠设备身份”的假设。项目继续把设备摘要和网络前缀标为辅助线索，不在通知中断言具体人员或精确位置；用户代理也不进入本轮通知事实。

该研究提出完整记录、固定术语、说明记录原因、提供可执行补救以及同时具备站内和站外界面等原则。项目据此区分三类东西：审计用于追责，账号页用于本人查看，独立通知用于账号可能已被接管时触达本人；三者不能相互冒充。也不对每次普通登录发通知，避免告警疲劳。

[Wei 等，NDSS 2025](https://www.ndss-symposium.org/ndss-paper/who-is-trying-to-access-my-account-exploring-user-perceptions-and-reactions-to-risk-based-authentication-notifications/)以 258 名线上和 15 名线下参与者研究由正确密码、错误密码和重置触发的 RBA 通知：46% 怀疑通知是钓鱼，65% 会进入账号查看，但未发现异常时不再处理。该研究不能证明某一通知模板适合教师，却说明“去活动页看看”不是完整补救。未来通知必须解释发生了什么、为何收到、如何限制访问和从可信入口完成后续动作。

[Sahin 等，NDSS 2025](https://www.ndss-symposium.org/ndss-paper/was-this-you-investigating-the-design-considerations-for-suspicious-login-notifications/)对 20 名美国参与者的半结构访谈发现，参与者重视详细、可行动信息，同时对邮件链接保持警惕。项目不直接外推其文案偏好；设计约束是通知无需点击即可理解，并提示教师自行打开已知的学校入口。未来若提供链接，只保留少量同源 HTTPS 链接且展示明确目的，不在邮件中要求输入密码、动态码或恢复码。

### 人工恢复不能退化为“管理员重置 MFA”

[Neil 等，SOUPS 2021](https://www.usenix.org/conference/soups2021/presentation/neil)将账号补救归纳为发现受损、恢复账号、限制已有访问、恢复服务和预防再次发生；其分析的 57 个服务中仅 39% 覆盖全部阶段。项目人工恢复运行手册必须逐项覆盖：冻结高影响操作、验证申请人与学校关系、双人审批、延迟生效并通知旧联系人、撤销所有会话／设备／因素、重新绑定、复核审计和事后回访。只有“找回密码”或“重置验证器”不算完成补救。

[FBI/CISA 联合公告 AA23-320A](https://www.ic3.gov/Media/News/2023/231116.pdf)记录了攻击者利用个人信息和社会工程诱导帮助台重置密码或 MFA、随后绑定攻击者因素的现实手法。行业事件不等同于本项目威胁发生率，但足以支持失败关闭：没有受控核验、职责分离和通知渠道前，不提供管理员一键清除 MFA，也不允许普通改密隐式删除因素。

### 本轮落地的可靠通知前置条件

- `auth.mfa_enabled`、`auth.mfa_recovery_used`、`auth.mfa_recovery_rotated`、`auth.mfa_disabled` 成功时生成版本化语义事实，并在同一数据库事务中写入审计、既有 `event_outbox` 和 `auth_security_notification_intent`。恢复码验证成功即记录“已使用”，即使用户随后取消关闭也不能静默消失。
- 通知待办固定为 `awaiting_channel`，只表示必须通知，不表示已找到联系人、已发送或已送达。当前 `LogPublisher` 即使发布成功，也不会更新或删除待办。外部渠道、联系人验证、模板、送达回执和退信仍未实现。
- 语义 payload 只允许事件 ID、schema 版本、租户、主体／操作者 ID、操作、验证方法与时间；不包含密码、TOTP 密钥、动态码、恢复码、挑战／会话摘要、IP、用户代理、邮箱或手机号。联系人以后由受控路由层按事件发生时的已验证地址解析，不能把地址复制进长期事件。
- [AWS 的 transactional outbox 指南](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)说明该模式消除业务写入与事件发布之间的双写缺口，但消费者仍须处理至少一次交付造成的重复。未来通知消费者必须以 `(event_id, recipient, channel)` 幂等去重，并为各渠道维护独立投递状态；不能用全局 `published_at` 推断“教师已收到通知”。
- `event_outbox` 中新的 `auth_mfa` 聚合与通知待办启用强制租户 RLS。请求作用域不能修改或删除已提交的 MFA 事实；维护调度器仍使用明确的 maintenance 上下文更新租约、重试和发布列。普通租户运行身份无上下文或错误租户时看不到这些安全事实。

本轮只建立不会丢失的通知义务，没有接入真实联系方式，不因此解除独立通知上线门槛。

## 验证口径

本轮用 Vitest 检查流程状态、请求范围、取消／过期／晚到响应、错误恢复和非自动执行，用 Playwright CLI 在真实浏览器中注入合成接口响应检查 UI。浏览器合成二维码只是安全 PNG 占位图，不表示真实手机扫码成功。真实 SQL、密码、OTP 加密、RLS 和事务防重放仍以 `e2e_mfa_test.go` 的隔离 PostgreSQL 专项为准；两者不能混称为完整生产端到端验收。浏览器截屏、下载和日志只能对合成资料保存，禁止对真实注册密钥和恢复码录屏或采集跟踪。
